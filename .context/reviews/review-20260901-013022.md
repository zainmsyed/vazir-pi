## Findings
### Finding 1
- Severity: high
- Category: test-gap
- Summary: The matrix does not execute the public installer for the advertised scenario set.
- Evidence: `scripts/validate-install-matrix.mts` declares ten `SCENARIOS`, but never dispatches on them. It only invokes `validate-install-activation.mts` and `validate-install-lifecycle.mts`, which are separate helper-level suites. The matrix therefore does not independently prove clean install/rerun/upgrade/failure behavior through `install.sh` or verify each listed scenario's exit status and diagnostic.
- Recommendation: Replace the unused scenario list with explicit scenario functions or invoke the installer-level harness for every scenario, asserting exit status, active version, failure diagnostic, and preservation after each run. Keep the matrix runner responsible for the scenarios it advertises.
- Rule candidate: A test matrix must execute and assert each scenario it declares; a label-only scenario list is not coverage.

### Finding 2
- Severity: high
- Category: test-gap
- Summary: The required WSL2 job is only a synthetic platform-contract test, not a WSL2 installation smoke test.
- Evidence: The `wsl2` GitHub Actions entry runs on `ubuntu-latest`, and `platformContract("wsl2")` injects the string `"microsoft WSL2"` into a fake `detectPlatform` probe. No WSL2 kernel, Linux-home policy, or installer invocation runs in that job. The documentation correctly calls it a “WSL2 contract seam,” but this does not satisfy the story's required WSL2 install coverage.
- Recommendation: Run the WSL2 job on an actual WSL2 environment (or a supported self-hosted WSL2 runner) and execute the installer matrix there. If hosted WSL2 is unavailable, make the job explicitly a non-required contract check and document the missing required smoke coverage rather than labeling it required.
- Rule candidate: Platform smoke jobs must execute on the platform they claim to validate; synthetic probes should be labeled contract tests.

### Finding 3
- Severity: medium
- Category: test-gap
- Summary: Preservation coverage checks only one marker file and omits important Pi state categories.
- Evidence: `preservationContract()` creates `.context`, `.pi`, and `.git` directories with a single `marker` file, then checks that marker after uninstall. It does not cover Pi credentials, settings, models, sessions, packages, or nested VCS metadata, and it does not compare directory contents byte-for-byte before and after the lifecycle.
- Recommendation: Seed representative nested files for credentials, settings, models, sessions, packages, and VCS metadata; snapshot their bytes before each lifecycle operation and compare the snapshots afterward. Keep all fixtures inside the temporary home.
- Rule candidate: Preservation tests should snapshot representative nested user-state files byte-for-byte, not only assert that a marker survives.
