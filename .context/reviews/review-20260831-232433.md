## Findings
### Finding 1
- Severity: high
- Category: bug
- Summary: Minisign verification is optional, so the default installer can activate unsigned artifacts.
- Evidence: `install.sh:83-90` sets `VERIFY_SIGNATURE=0` when `VAZIR_MINISIGN_PK` is unset, and `install.sh:141-163` downloads and verifies the `.minisig` file only when that flag is enabled. The default release URL therefore activates an artifact after checksum verification without signature verification, contrary to the story goal.
- Recommendation: Fail closed unless a trusted minisign public key is available from a non-user-controlled trust-root mechanism, always download the signature, and require minisign verification before extraction/activation. Keep key provisioning separate, but do not provide an unsigned default path.
- Rule candidate: Security-critical release verification must fail closed when a required trust root is unavailable.

### Finding 2
- Severity: high
- Category: bug
- Summary: Manifest identity is not bound to the requested version or detected target.
- Evidence: The embedded validator in `install.sh:222-258` checks manifest shape, file hashes, and required files, but never compares `manifest.vazirVersion` with `RELEASE_VERSION` or `manifest.platform`/`architecture`/`libc` with `ARTIFACT_TARGET`. `src/install/verify.ts:72-139` has the same omission. A valid artifact for a different version or platform can therefore be activated under the requested release path.
- Recommendation: Pass expected release metadata into manifest verification and require exact matches for version, OS, architecture, libc, bundled Node version, and Pi version before activation. Add mismatched-identity regression cases.
- Rule candidate: —

### Finding 3
- Severity: high
- Category: bug
- Summary: Activation failure can delete or orphan the currently active release.
- Evidence: `install.sh:264-276` removes an existing `releases/<version>` before committing the new active link. Its macOS fallback then performs `rm -f "$INSTALL_ROOT/active"` before moving the temporary link. If the move or symlink operation fails, the old active link may be gone; reinstalling the currently active version can also delete the only active release before the switch. `src/install/staging.ts:46-60` similarly removes an existing release before switching and has no rollback path.
- Recommendation: Keep the old release and active link intact until the new release has been moved into a unique staging sibling and the active-link replacement has succeeded. Use a platform-safe atomic replacement, and fail without deleting `active` if atomic replacement is unavailable. Add forced activation-failure coverage.
- Rule candidate: Activation should be commit-last: never delete the current active pointer or release until the replacement is durably ready.

### Finding 4
- Severity: medium
- Category: test-gap
- Summary: The regression suite does not exercise real minisign cryptography or activation-failure atomicity.
- Evidence: `scripts/validate-install-activation.mts:108-151` creates a shell fake `minisign` that compares a public-key string and SHA-256 text; it does not parse or verify an actual minisign signature. The integration cases at `scripts/validate-install-activation.mts:305-395` cover download/checksum/signature/extraction/manifest/self-test/lock failures, but none forces the final release move or active-link replacement to fail while an existing release is active.
- Recommendation: Add a fixture using the real minisign implementation when available (or a cryptographically faithful verifier test), explicitly test missing-key/signature fail-closed behavior, and inject a final activation failure to assert that the old `active` target and valid release remain unchanged.
- Rule candidate: —
