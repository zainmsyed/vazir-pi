## Findings

### Finding 1
- **Severity:** low
- **Category:** bug
- **Summary:** The in-progress review notification still promised to prompt "when the review stalls", but the stalled-review prompt was removed.
- **Evidence:** `.pi/extensions/vazir-context/complete-story.ts` notified: `"${storyLabel} review is still in progress... Vazir will prompt when the review stalls or is marked complete."` Since the stalled fallback prompt was removed, only the `complete` path is real.
- **Recommendation:** Update the notification wording to `"Vazir will prompt when the review is marked complete."`
- **Rule candidate:** Keep UI copy aligned with actual handler behavior; leftover phrasing from removed prompts becomes misleading.

### Finding 2
- **Severity:** medium
- **Category:** bug
- **Summary:** The manual `/review` closeout path had no way to resume a completed review that was suspended after the user deferred the closeout prompt.
- **Evidence:** `.pi/extensions/vazir-context/index.ts` `/review` always started a new review flow, replacing any pending manual closeout state. A completed-but-suspended review could only be closed if its file hash changed, leaving no explicit resume path.
- **Recommendation:** Add a UI prompt in `/review` that detects a completed-but-suspended manual review and offers to resume the closeout or start a new review. Selecting "Resume closeout" clears `suspended` so the next `turn_end` prompts for closeout.
- **Rule candidate:** Explicit commands that replace shared workflow state should give the user a way to finish an already-completed closeout before discarding it.

### Finding 3
- **Severity:** low
- **Category:** test-gap
- **Summary:** The new regression test for completed-but-suspended review resume did not reproduce the exact matching-hash deadlock.
- **Evidence:** `scripts/validate-vazir-active-review-suppression.mts` seeded `reviewFileHash: "deadbeef"`, which differs from the current review hash. The real failure happened when the persisted hash already matched the current file (`suspended && !changed`).
- **Recommendation:** Add a second scenario (or assertion) where `reviewFileHash` equals the actual current review hash and `reviewSuspended: true`, then verify the closeout prompt still appears.
- **Rule candidate:** Regression tests should reproduce the exact stale-state signature that triggered the bug, not only a changed-file path.

### Finding 4
- **Severity:** low
- **Category:** dead-code
- **Summary:** `processCompleteStoryReviewCloseout` checked `decision === "not-yet"` twice; the second check was unreachable.
- **Evidence:** `.pi/extensions/vazir-context/complete-story.ts` returned early on `if (decision == null || decision === "not-yet")`, then later contained another `if (decision === "not-yet") return true;` after the `fix-high`/`fix-all` branches.
- **Recommendation:** Remove the redundant second check.
- **Rule candidate:** Remove duplicate guard clauses that become unreachable after early returns.

### Finding 5
- **Severity:** low
- **Category:** regression
- **Summary:** `handleTurnEnd` returned `true` for every in-progress review boundary, even when it took no action.
- **Evidence:** `.pi/extensions/vazir-context/complete-story.ts` `handleTurnEnd` review-in-progress branch ended with `return true;`. In `.pi/extensions/vazir-context/index.ts`, `if (await completeStoryController.handleTurnEnd(ctx)) return;` short-circuited the rest of `turn_end`, so passive observation could suppress later handlers such as the plan story fix check and newly-completed story handling.
- **Recommendation:** Return `false` when the review is merely observed to be in progress and no prompt or internal message was dispatched; reserve `true` for actual work.
- **Rule candidate:** Lifecycle handlers should return "handled" only when they actually performed work; passive observation should not starve downstream hooks.

### Finding 6
- **Severity:** low
- **Category:** workflow
- **Summary:** The story-064 checklist marked the interactive smoke check as done before it was actually exercised.
- **Evidence:** `.context/stories/story-064.md` checklist contained `[x] Run targeted validation plus an interactive smoke check of /complete-story → review → close` while only targeted validations had been run.
- **Recommendation:** Run the live `/complete-story` → "Start code review before closing" → close path (or an equivalent harness simulation) and mark the checklist item complete only after it passes.
- **Rule candidate:** Do not mark interactive verification steps complete without actually exercising the UI path.

### Finding 7
- **Severity:** low
- **Category:** simplification
- **Summary:** `reviewFileHash` used a weak 32-bit signed integer hash to gate workflow transitions.
- **Evidence:** `.pi/extensions/vazir-context/helpers.ts` implemented a custom 32-bit hash with `hash = ((hash << 5) - hash) + char; hash |= 0;`. Hash collisions could make a changed review file look unchanged, keeping a review suspended or suppressing a closeout prompt.
- **Recommendation:** Replace it with a robust checksum such as `crypto.createHash("sha256")` over the file contents.
- **Rule candidate:** Use cryptographic or checksum hashes when file-change detection gates user-facing workflow transitions.
