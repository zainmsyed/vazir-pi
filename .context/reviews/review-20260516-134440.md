## Findings

### Finding 1 — Review instructions never tell the agent to create a `## Fallow Findings` section

- **Severity:** medium
- **Category:** workflow
- **Evidence:**
  - `reviewFileTemplate` (helpers.ts) does not include a `## Fallow Findings` section.
  - `buildReviewInstruction` (helpers.ts) prepends the static-analysis prompt block but never instructs the agent to preserve Fallow findings in a dedicated section.
  - The agent is told to "synthesise" static-analysis findings into its own inspection, which means they typically land under `## Findings` with Severity/Category/Evidence format, not under a separate `## Fallow Findings` heading.
  - `reviewFallowFindingsFromFile` (helpers.ts) only parses lines under `## Fallow Findings`. If the agent never creates that section, the parser returns `[]` and `appendFallowToComplaintsLog` never fires.
- **Recommendation:** Add a `## Fallow Findings` placeholder to `reviewFileTemplate` and add an explicit instruction in `buildReviewInstruction` telling the agent to copy verbatim Fallow findings into that section (or write `No Fallow findings` if none exist).
- **Rule candidate:** When a backend produces structured findings that must be parsed later, the review template and instructions must explicitly direct the agent to preserve them in the expected section.

### Finding 2 — Fossil bridge copies Vazir internal directories into the temp git repo

- **Severity:** low
- **Category:** workflow
- **Evidence:**
  - `runFallowAuditViaFossilBridge` (index.ts) uses `copyContents(cwd, repoDir)` with an `excluded` set of `{".git", "node_modules", ".jj", ".fslckout", "_FOSSIL_", "dist", "build", "out"}`.
  - `.context/` is not excluded, so `.context` files are copied into the temp repo and committed.
  - Fallow running with `--base HEAD~1` will see `.context` files as new additions (since Fossil ignore-glob keeps them out of Fossil history) and may analyze them, producing noise or false positives in Vazir metadata.
- **Recommendation:** Add `.context` to the `excluded` set in `copyContents` so the temp repo mirrors only source and config files.
- **Rule candidate:** When creating a temp mirror of a repo for external tooling, exclude the project's own brain/metadata directories to prevent the tool from analyzing generated or internal files.

### Finding 3 — `appendFallowToComplaintsLog` re-reads the log file instead of reusing in-memory parse

- **Severity:** low
- **Category:** simplification
- **Evidence:**
  - `appendFallowToComplaintsLog` (helpers.ts) parses `existingEntries` from the in-memory `lines` array for deduplication.
  - It then calls `countFallowOccurrences(cwd, finding.key)` (helpers.ts), which performs a fresh `readIfExists(complaintsLogPath(cwd))` and re-parses every line.
  - In a single-threaded runtime this is harmless but wasteful; the count could be derived from `existingEntries` directly.
- **Recommendation:** Compute the occurrence count from `existingEntries` instead of calling `countFallowOccurrences` inside the append loop, or inline the counting logic to avoid the extra disk read.
- **Rule candidate:** Avoid re-reading a file you already have parsed in memory; derive secondary computations from the in-memory representation.

### Finding 4 — `parseComplaintsLogFallowEntry` regex is rigid against future format extensions

- **Severity:** low
- **Category:** workflow
- **Evidence:**
  - The regex `/^([^|]+)\|\s*([^|]+)\|\s*\[fallow\]\s*(.+?)\s*\|\s*status:\s*([^|]+?)\s*$/i` anchors to end-of-line with `$`.
  - If the complaints-log format ever gains trailing fields (e.g., `| count: 3`), the regex will fail to match and the entry becomes invisible to recurrence counting.
- **Recommendation:** Relax the regex by removing the `$` anchor or making the status capture non-greedy and allowing trailing content: `/status:\s*([^|]+)/i`.
- **Rule candidate:** When parsing pipe-delimited log lines, do not anchor the regex to end-of-line unless the format is guaranteed frozen; allow benign trailing fields.
