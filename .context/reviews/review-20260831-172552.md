## Findings

### Finding 1
- Severity: high
- Category: bug
- Summary: The shell installer and the TypeScript platform detector disagree on Linux artifact target names.
- Evidence: `install.sh` assigns `ARTIFACT_TARGET="linux-x64"`, while `src/install/platform.ts` returns `"linux-x64-gnu"` for glibc Linux. The same mismatch exists for musl (`"linux-arm64"` vs `"linux-arm64-musl"`). When the installer later downloads an artifact, it will request a filename that the release pipeline does not produce.
- Recommendation: Align both layers on the same artifact naming scheme. If the release manifest uses libc-qualified Linux targets, update `install.sh` to append `-gnu`/`-musl`. If release artifacts are unqualified, update `platform.ts` to drop the libc suffix for artifact names while keeping libc in diagnostics.
- Rule candidate: Installer and runtime artifact naming must be derived from the same release manifest schema; never hard-code target strings in more than one place.

### Finding 2
- Severity: low
- Category: bug
- Summary: The WSL2 environment label in `install.sh` prints nothing.
- Evidence: The echo line is `echo "    Detected: ${IS_WSL2:+}${HOST_OS}/${HOST_ARCH} ..."`. The `${IS_WSL2:+}` parameter expansion substitutes the empty string when `IS_WSL2` is non-empty, so "WSL2" never appears in output.
- Recommendation: Change to `${IS_WSL2:+WSL2 }` or use an explicit `if [[ "$IS_WSL2" == "1" ]]; then echo -n "WSL2 "; fi` block.
- Rule candidate: —

### Finding 3
- Severity: medium
- Category: bug
- Summary: The default `commandAvailable` probe only checks file existence, not executability.
- Evidence: `src/install/platform.ts` uses `fs.existsSync("${entry}/${command}")`. A non-executable file or directory named `curl` would be reported as available, causing the preflight to pass and a later spawn to fail.
- Recommendation: Use `fs.accessSync(path, fs.constants.X_OK)` inside a try/catch, or fall back to a process spawn probe.
- Rule candidate: Tool-availability checks must verify the executable bit, not just path presence.

### Finding 4
- Severity: medium
- Category: bug
- Summary: Unrecognized preflight failure codes are misreported as "unsupported-platform".
- Evidence: `diagnosticFor` in `src/install/diagnostics.ts` returns the `unsupported-platform` diagnostic for any code not in the table or not matching `missing-tool:*`. A future preflight failure such as `disk-full` would be labeled as an unsupported platform.
- Recommendation: Add a dedicated `unknown-preflight-failure` diagnostic code for the fallback case, or validate known codes at build/test time and throw on truly unexpected input.
- Rule candidate: Fallback diagnostics must not impersonate a specific, user-facing error category.

### Finding 5
- Severity: medium
- Category: test-gap
- Summary: Preflight warnings have no formatter or display path.
- Evidence: `evaluatePreflight` produces `warnings` such as `existing-pi-installation`, but `formatDiagnostics` only formats `failures`. The warning exists in data but never reaches the user in a structured way.
- Recommendation: Add `formatWarnings` (or extend `formatDiagnostics` to accept warnings) and assert in tests that warnings render with the correct code, message, and remediation.
- Rule candidate: Every preflight signal that is surfaced to the user must have a tested display path.

### Finding 6
- Severity: low
- Category: test-gap
- Summary: Preflight validation does not exercise musl/Alpine Linux detection.
- Evidence: `scripts/validate-install-preflight.mts` only tests Ubuntu/glibc (`ID=ubuntu`, `ldd` present). The `libc: "musl"` branch and `/etc/alpine-release` branch are uncovered.
- Recommendation: Add a probe case with `/etc/alpine-release` present and `ldd` returning musl text, asserting `libc: "musl"` and an artifact target ending in `-musl`.
- Rule candidate: —

### Finding 7
- Severity: low
- Category: test-gap
- Summary: `install.sh` requires `chmod` but the TypeScript validation does not cover it.
- Evidence: `install.sh` lists `curl tar mktemp chmod` as required tools. The validation test only checks `curl`, `tar`, and `mktemp`, and `evaluatePreflight` has no special handling for `chmod`.
- Recommendation: Either add `chmod` to the validation test matrix or remove `chmod` from the installer prerequisite list if the installer does not actually need it in story-076 scope. If it is needed later, document it as a dependency of the activation story.
- Rule candidate: Required-tool lists in shell installers and their TypeScript validators must stay in sync.
