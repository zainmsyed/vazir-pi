## Findings

### Finding 1
- Severity: high
- Category: bug
- Summary: Rollback and release retention still rely on GNU-only `readlink -f`, breaking the macOS portability goal of story-083.
- Evidence: `install.sh` lines 52 and 476 call `readlink -f "$INSTALL_ROOT/active"`. The BSD/macOS `readlink` binary does not support `-f`, so `lifecycle_rollback` and the post-activation retention loop fail on stock macOS even though the `mv` path was made portable.
- Recommendation: Resolve the active symlink target without `-f`. Since `replace_active_link` always creates `active` as a relative symlink (`releases/<version>`), use `readlink "$INSTALL_ROOT/active"` and resolve it relative to `INSTALL_ROOT`, or add a small POSIX helper. Update the BSD stub regression to exercise this path as well.
- Rule candidate: Shell scripts that claim macOS portability must not use GNU-specific `readlink -f` without a portable fallback.

### Finding 2
- Severity: low
- Category: dead-code
- Summary: The activation failure path cleans up a temporary symlink name left over from the previous implementation.
- Evidence: `install.sh` line 467 runs `rm -f "$INSTALL_ROOT/active.tmp"` after `replace_active_link` fails, but the shared helper now uses `.active.tmp.install.$$` and removes its own temporary symlink on failure.
- Recommendation: Remove the stale `rm -f "$INSTALL_ROOT/active.tmp"` line from the activation failure path.
- Rule candidate: —

### Finding 3
- Severity: low
- Category: bug
- Summary: `scripts/validate-install-lifecycle.mts` leaks the temporary `mv` stub directory.
- Evidence: The test creates `mvStubDir` with `fs.mkdtempSync` but only removes `home` at the end of the script; `mvStubDir` is never deleted.
- Recommendation: Add `fs.rmSync(mvStubDir, { recursive: true, force: true })` before the final cleanup, matching the cleanup already present in `validate-install-activation.mts`.
- Rule candidate: —

### Finding 4
- Severity: low
- Category: simplification
- Summary: The BSD-compatible `mv` stub helper is duplicated across both install validation scripts.
- Evidence: `createMvStub()` is defined identically in `scripts/validate-install-lifecycle.mts` and `scripts/validate-install-activation.mts`.
- Recommendation: Move `createMvStub` into a shared test helper (e.g. `scripts/lib/validation-harness.mts` or a new `scripts/lib/install-test-helpers.mts`) and import it in both scripts.
- Rule candidate: Shared test fixtures should live in one place and be imported where needed.
