## Findings
### Finding 1
- Severity: critical
- Category: test-gap
- Summary: Runtime manifest verification has very high branching complexity without direct coverage, making release-integrity regressions difficult to detect.
- Evidence: Fallow reports `src/install/verify.ts:79` `verifyRuntimeManifest` at cyclomatic 39, cognitive 42, CRAP 1560, with no recorded coverage. The function combines manifest shape checks, declared/actual file comparison, content hashing, required-artifact checks, and lockfile validation in one path.
- Recommendation: Split `verifyRuntimeManifest` into focused validators and add direct tests for missing files, extra files, hash mismatches, lockfile mismatches, malformed manifests, and required runtime assets.
- Rule candidate: Security-critical validation should have direct branch coverage for every rejection category.

### Finding 2
- Severity: critical
- Category: test-gap
- Summary: Platform detection and preflight decision logic have high complexity but no direct coverage according to Fallow.
- Evidence: Fallow reports `src/install/platform.ts:64` `detectPlatform` at cyclomatic 24 / CRAP 600, `detectLibc` at cyclomatic 16 / CRAP 272, and `evaluatePreflight` at cyclomatic 14 / CRAP 210, all with no recorded coverage. These functions control supported OS/architecture/libc selection and installer rejection behavior.
- Recommendation: Add focused tests for Linux glibc and musl, macOS architectures, WSL2, unsupported architectures, unknown libc, missing tools, unwritable paths, and conflicting installations; then simplify the branching where practical.
- Rule candidate: Installer platform gates need coverage across every supported and rejected environment branch.

### Finding 3
- Severity: medium
- Category: simplification
- Summary: Manifest verification duplicates hashing, recursive file enumeration, and manifest comparison logic across two modules.
- Evidence: Fallow reports clone groups between `src/install/verify.ts` and `src/runtime/manifest.ts` for SHA-256 streaming, `relativeFiles`, declared-vs-actual file checks, and content-hash validation.
- Recommendation: Move the shared primitives into a neutral runtime/install helper and retain only the different error-reporting policy in each caller. Add a direct combined test covering hashing, file enumeration, and validation together.
- Rule candidate: When two release-validation paths perform the same filesystem operation, consolidate the operation in one shared helper and test the combined contract.

### Finding 4
- Severity: low
- Category: dead-code
- Summary: The installer modules expose a large set of exports and types that Fallow cannot trace to runtime entry points, and Fallow also flags the Pi dependency as unused.
- Evidence: Fallow reports 8 unused value exports, 22 unused exported types, and `@earendil-works/pi-coding-agent` as an unused dependency. Several exports are intentionally consumed by validation scripts or dynamic runtime loading, so this is partly a static-analysis reachability limitation, but the report indicates the public surface is not documented or mechanically checked.
- Recommendation: Classify intentional public/test exports with an explicit entry-point or ignore configuration, and remove only exports confirmed to have no callers. Add a dependency smoke check proving the bundled Pi package is required at runtime.
- Rule candidate: Static dead-code findings on dynamically loaded or test-facing APIs must be reconciled against real consumers before removal.
