## Findings
### Finding 1
- Severity: high
- Category: bug
- Summary: Lifecycle entrypoints bypass the install lock.
- Evidence: `install.sh` handles `--rollback` and `--uninstall` before creating `$INSTALL_ROOT/.install.lock`; `src/install/lifecycle.ts` also performs rollback/uninstall without acquiring a lock. A concurrent upgrade can replace `active` while rollback is selecting a target, and uninstall can remove the root while an upgrade is extracting or activating.
- Recommendation: Share the existing lock protocol across install, rollback, and uninstall, and hold it for the full lifecycle operation. Add a concurrent-operation regression test that proves one operation fails safely without corrupting `active` or a release directory.
- Rule candidate: Lifecycle mutations must acquire the same per-install lock for their entire operation, including rollback and uninstall.

### Finding 2
- Severity: high
- Category: bug
- Summary: The migration implementation only detects legacy state; it does not migrate it.
- Evidence: `migrateExistingInstallation()` is a direct alias for `detectExistingInstallation()` and returns an inventory without copying, linking, importing, or recording any migration result. `install.sh` only prints a notice when `$HOME/.vazir` or `$HOME/.config/vazir` exists. Thus an existing installation is detected but no migration entrypoint actually preserves/adopts its runtime or state into the new layout.
- Recommendation: Define the supported legacy layouts and implement an additive migration plan that copies or adopts only Vazir-owned runtime data, never overwriting existing user files. Return a migration result with copied/skipped paths and test an old installation through the shell entrypoint.
- Rule candidate: Detection is not migration; migration APIs must report concrete additive actions and skipped conflicts.

### Finding 3
- Severity: medium
- Category: bug
- Summary: Uninstall does not remove a managed launcher installed in a custom bin directory.
- Evidence: Installation honors `VAZIR_BIN_DIR` and writes the launcher to `$BIN_DIR/vazir`, but `lifecycle_uninstall()` only checks and removes `$HOME/.local/bin/vazir`. The TypeScript `uninstall()` helper does not remove any launcher. A custom-bin uninstall therefore leaves a stale managed executable behind.
- Recommendation: Persist or derive the configured launcher path consistently and remove it only after verifying it is Vazir-managed. Cover both default and custom `VAZIR_BIN_DIR` uninstall paths.
- Rule candidate: Cleanup must use the same configurable ownership path used by installation and must verify ownership before deletion.

### Finding 4
- Severity: medium
- Category: test-gap
- Summary: Regression coverage does not exercise the public shell lifecycle entrypoints.
- Evidence: `scripts/validate-install-lifecycle.mts` tests TypeScript helpers with synthetic release directories, but does not invoke `install.sh --rollback` or `install.sh --uninstall`, does not test custom install/bin roots, does not test lock contention, and does not verify the failed-upgrade shell path preserves a runnable prior release. The shell entrypoints contain separate logic from the TypeScript helpers and can regress independently.
- Recommendation: Extend the isolated validation to invoke the shell entrypoints in temporary homes, including failed upgrade, rollback, repeated rollback/uninstall, lock contention, custom paths, and preservation of project `.context/`, Pi state, and VCS metadata.
- Rule candidate: Shell entrypoints need isolated integration coverage separate from helper-level tests.

### Finding 5
- Severity: medium
- Category: bug
- Summary: Rollback and uninstall are not protected against stale temporary activation paths.
- Evidence: `lifecycle_rollback()` creates `$INSTALL_ROOT/.active.tmp.$$` without first removing a stale path. A crashed prior rollback with the same PID or a pre-existing temporary path causes `ln -s` to fail under `set -e`. `atomicActivate()` removes its temporary path, but the shell implementation does not share that behavior.
- Recommendation: Use a unique temporary name, remove only a known-safe stale temporary path before use, and clean it on failure. Prefer one shared atomic activation implementation or add a shell regression for interrupted rollback recovery.
- Rule candidate: Atomic pointer updates must be restart-safe and clean their temporary pointer on every failure path.
