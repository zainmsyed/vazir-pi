## Findings
### Finding 1
- Severity: medium
- Category: bug
- Summary: The repair state is seeded on `/plan` but cleared on the first `agent_end`, which during a normal multi-turn planning conversation is the clarifying-question turn — before any stories are actually written. This causes the repair loop to self-destruct before it can validate newly generated stories.
- Evidence: `before_agent_start` sets `pendingPlanRepairRequests` when `isPlanPrompt` matches. `agent_end` deletes it if `listStoryValidationIssues(cwd)` returns empty. During a fresh `/plan`, the agent typically asks 1–3 clarifying questions before writing stories. Each question turn fires `agent_end`. If no story files exist yet (fresh plan), `issues.length === 0`, so the state is silently deleted. When stories are finally written in a later turn, no repair state is active and malformed output is never caught. The same problem affects replans where existing stories are valid — the state is cleared on the first clarifying-question `agent_end` and never re-seeded.
- Recommendation: Track the number of story files present when `/plan` starts (e.g. `storyCountAtStart`). In `agent_end`, only validate (and potentially clear state) when the story count has changed since `/plan` began OR when at least one repair attempt has already been dispatched (`retries > 0`). This keeps the state alive through clarifying questions and activates validation only after the agent has actually written stories.
- Rule candidate: When a workflow transition depends on both in-memory flags and persisted file frontmatter, centralize the transition in one shared helper so both state sources change together.

### Finding 2
- Severity: low
- Category: simplification
- Summary: `pendingPlanRepairRequests.set(cwd, planRepair)` after incrementing `retries` is a no-op because `planRepair` is a mutable object reference already held by the Map.
- Evidence: `.pi/extensions/vazir-context/index.ts:1323` — `planRepair.retries += 1; pendingPlanRepairRequests.set(cwd, planRepair);` The object retrieved by `.get()` is mutated in place; the subsequent `.set()` stores the same reference back into the same key.
- Recommendation: Remove the redundant `.set()` call.

### Finding 4
- Severity: low
- Category: test-gap
- Summary: No test covers the multi-turn planning conversation where clarifying questions precede story generation.
- Evidence: All four tests call `before_agent_start` with `/plan` and then immediately call `agent_end`. None simulate an intervening clarifying-question turn that fires `agent_end` before stories exist. This gap allowed the state-clearing bug in Finding 1 to go undetected.
- Recommendation: Add a test that simulates a clarifying-question turn (no stories written yet) followed by the story-writing turn, verifying the repair state survives the first `agent_end` and activates on the second.
- Rule candidate: When adding lifecycle state machines that span multiple turns, add regression coverage for every intermediate state transition, not just the final outcome.

### Finding 5
- Severity: low
- Category: bug
- Summary: The retry-exhaustion error notification repeats filenames when a single story has multiple validation issues.
- Evidence: `.pi/extensions/vazir-context/index.ts:1331` — `issues.map(i => path.relative(cwd, i.file)).join(", ")` iterates over every issue, not every unique file. A story with both invalid status and malformed checklist produces `.context/stories/story-001.md, .context/stories/story-001.md`.
- Recommendation: Deduplicate the file list with `[...new Set(issues.map(i => path.relative(cwd, i.file)))].join(", ")`.
