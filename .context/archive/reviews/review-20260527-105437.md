## Findings

### Finding 1
- Severity: medium
- Category: bug
- Summary: Restoring from one pending complete-story session to a different pending story can still leave Vazir blind to the restored pending state until the user reruns `/complete-story`.
- Evidence: In `.pi/extensions/vazir-context/complete-story.ts`, `resolvePendingCompleteStoryRequest(...)` sets `const targetStoryFile = storyFile ?? existing?.storyFile;`. When `handleTurnEnd()` or `handleAgentEnd()` calls it without a `storyFile`, a stale in-memory request for story A forces the function down the `targetStoryFile` branch. If JJ restore removed A’s persisted closeout marker and restored story B’s marker instead, the function deletes the stale A entry and immediately returns `null` without falling through to `listPersistedCompleteStoryCloseoutStates(cwd)`. That means the restored pending state for story B is skipped on that turn.
- Recommendation: After clearing a stale in-memory request whose persisted marker no longer exists, continue scanning restored closeout state files instead of returning early. Add a direct restore scenario where memory points at story A but the restored `.context` marker belongs to story B.
- Rule candidate: When reconciling restored disk state with stale in-memory workflow state, do not stop after clearing the stale entry; continue searching for the restored authoritative state in the same pass.

### Finding 2
- Severity: low
- Category: test-gap
- Summary: The new JJ restore regressions only cover same-story phase rewind and no-marker cleanup; they do not cover the cross-story pending-state swap that exposes the stale-entry early-return bug.
- Evidence: `scripts/validate-vazir-complete-story.mts` adds `runJjRestoreResyncReviewCloseoutScenario()` and `runJjRestoreClearsStalePendingScenario()`. Both keep the same `storyPath` before and after restore. There is no scenario where in-memory pending state references one story, the restored `.context` marker references a different story, and the controller is expected to resume that restored story immediately.
- Recommendation: Add a real-JJ restore scenario with two stories: persist a pending closeout marker for story B, mutate in-memory state to story A, restore to B’s op, then assert `handleTurnEnd()` or `handleAgentEnd()` resumes story B without requiring a new `/complete-story` command.
- Rule candidate: Restart/restore regression coverage for persisted workflow state should verify both same-story phase rewinds and cross-story state replacement, because stale memory can point at a different entity than the restored disk state.

## Completion Summary
Both recommended fixes are complete.

1. **Cross-story restore blind spot fixed** — `resolvePendingCompleteStoryRequest(...)` in `.pi/extensions/vazir-context/complete-story.ts` now keeps scanning restored closeout state after clearing a stale in-memory story entry, unless the caller explicitly requested a specific `storyFile`. This lets `turn_end` and `agent_end` recover immediately when JJ restore swaps the authoritative pending closeout marker from one story to another.

2. **Cross-story real-JJ regression added** — `scripts/validate-vazir-complete-story.mts` now includes `runJjRestoreCrossStoryPendingSwapScenario()`, which:
   - persists a pending closeout marker for story-002,
   - mutates in-memory pending state to story-001,
