## Findings

### Finding 1
- Severity: medium
- Category: bug
- Summary: `promptLearnedRulePromotion` fallback matching can promote the wrong rule when option strings share a prefix.
- Evidence: `.pi/extensions/vazir-story/index.ts` lines ~891–900: the fallback uses `opt.startsWith(choice) || choice.startsWith(opt)`. If a user selects "Promote rule 1" but the TUI returns a truncated or prefix-matched string, and "Promote rule 10" also exists, the match is ambiguous.
- Recommendation: Remove the prefix fallback entirely, or restrict it to exact prefix matches only when the choice string is the full option text. The number-parsing fallback below it (`/\d+/`) is already sufficient for numeric selections.
- Rule candidate: When adding fuzzy-match fallbacks for user selections, require an exact match or a single unambiguous token rather than mutual prefix matching that can collide with sibling options.

### Finding 2
- Severity: low
- Category: simplification
- Summary: `resolvePreferredVcsKind` contains duplicate preference checks for `"jj"` and `"git"`.
- Evidence: `.pi/extensions/vazir-vcs/index.ts` lines 123–130: `if (vcsPreference === "jj" && useJJ) return "jj";` appears twice (lines 124 and 127), and `if (vcsPreference === "git" && hasGitRepo) return "git";` at line 125 is shadowed by the unconditional `if (vcsPreference === "git") return "git";` at line 129.
- Recommendation: Collapse the duplicate checks into a single pass: first check with repo guard, then fall through to the unconditional return for the same preference.
- Rule candidate: When a preference-resolution function has the same condition repeated with and without a guard, merge them into one ordered branch list.

### Finding 3
- Severity: low
- Category: scope-drift
- Summary: The neutral `.pi/lib/vazir-vcs-helpers.ts` module exports names that still reference the old owner (`tracker`).
- Evidence: `.pi/lib/vazir-vcs-helpers.ts` exports `TRACKER_VCS_WORKFLOW_BOUNDARY` and `trackerVcsWorkflowScaffoldSummary`. These names predate the extraction and now live in a shared library that has no affiliation with `vazir-tracker`.
- Recommendation: Rename the exports to `VCS_WORKFLOW_BOUNDARY` and `vcsWorkflowScaffoldSummary`, or remove them if they are superseded by the equivalents already declared in `vazir-vcs/index.ts`.
- Rule candidate: When moving code into a neutral shared module, rename owner-specific identifiers so the module does not falsely advertise a dependency on a particular consumer.

### Finding 4
- Severity: low
- Category: workflow
- Summary: Both `vazir-story` and `vazir-vcs` register `input` handlers that write the last user prompt to the same global mutable state.
- Evidence: `.pi/extensions/vazir-story/index.ts` line 102 calls `setLastUserPrompt(event.text.trim())` for non-slash input. `.pi/extensions/vazir-vcs/index.ts` line 672 does the exact same thing. Both handlers fire on every non-command user message.
- Recommendation: Remove the prompt-capture logic from `vazir-vcs` and let `vazir-story` own it exclusively, since story lifecycle is the semantic owner of user prompt tracking.
- Rule candidate: When the same side-effecting state update appears in two event handlers, keep it in the extension whose domain concept owns that state.

### Finding 5
- Severity: low
- Category: test-gap
- Summary: No validation script exercises the resume-from-learned-rule-draft shortcut added to `handleCompleteStoryCommand`.
- Evidence: `scripts/validate-vazir-complete-story.mts` tests the happy path, the skip path, and the blocked-after-readiness path, but none of its scenarios seed a pre-existing `-learned-rule-closeout.json` draft and then call `/complete-story` a second time.
- Recommendation: Add a scenario that writes a valid draft JSON to `.context/reviews/`, then invokes the command handler again and asserts that the promotion picker appears immediately without re-sending the internal closeout instruction.
- Rule candidate: Every new resume/shortcut path in a state machine needs a dedicated regression test that proves the shortcut triggers the expected next state.

### Finding 6
- Severity: low
- Category: workflow
- Summary: `agent_end` in `vazir-vcs` silently discards errors from JJ checkpoint labeling and description.
- Evidence: `.pi/extensions/vazir-vcs/index.ts` lines 825–835 wrap `persistCurrentJjCheckpointLabel` and `autoDescribeCurrentJjChange` in empty `catch` blocks. If JJ is misconfigured or the op log format changes, the failure is invisible.
- Recommendation: Log the error message at `info` or `warning` level so users know when checkpoint metadata is not being preserved.
- Rule candidate: When silencing expected errors in a lifecycle hook, still emit a diagnostic so silent failures do not hide environmental or tooling regressions.
