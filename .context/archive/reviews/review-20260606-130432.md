## Findings
### Finding 1
- Severity: medium
- Category: regression
- Summary: `parseStoryFrontmatter()` and `listStories()` were made strictly validating, causing structurally incomplete stories to silently disappear from all workflow consumers instead of only the explicit guard/repair paths.
- Evidence: `parseStoryFrontmatter()` now delegates to `validateStoryFile().frontmatter`, which returns `null` when required sections are missing or the checklist is malformed. `listStories()` uses the same path and filters out any story that fails validation. A story missing a single required section like `## Out of scope` or with an empty checklist now vanishes from the story picker, active-story resolution, and `/implement` candidate lists without any user-visible explanation.
- Recommendation: Restore `parseStoryFrontmatter()` and `listStories()` to lenient parsing so stories remain visible. Keep `validateStoryFile()` and `listStoryValidationIssues()` strict, and have explicit guard/repair callers opt into strict validation rather than forcing it on every story-read path.
- Rule candidate: Keep shared data-structure parsers lenient by default so downstream consumers do not silently lose records; reserve strict validation for explicit guard, repair, and closeout paths where the caller intentionally opts in.

### Finding 2
- Severity: low
- Category: simplification
- Summary: The `/implement` guard message includes the story basename twice because `first.message` already embeds the filename.
- Evidence: `formatStoryValidationGuardMessage` joins `relativePath` with `first.message`, but `first.message` was built with `path.basename(filePath)` already in the text, producing output like `.context/stories/story-002.md: story-002.md has invalid status ...`.
- Recommendation: Build validation messages without embedding the basename, or strip it when composing the guard message, so the final warning reads cleanly.
