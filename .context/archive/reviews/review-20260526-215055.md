## Findings

### Finding 1
- Severity: medium
- Category: test-gap
- Summary: The exact-restore validation covers file modification, creation, and deletion, but omits the file-rename case — a representative changed-file state that JJ tracks differently from simple edits.
- Evidence: `scripts/validate-vazir-jj-exact-restore.mts` defines `runExactRestoreScenario` (modify + create) and `runDeleteFileRestoreScenario` (delete). There is no scenario where a file is renamed during the agent run and then restored to verify the old name reappears and the new name disappears.
- Recommendation: Add a `runRenameFileRestoreScenario` that creates `oldname.txt`, captures the pre-run op, renames it to `newname.txt` during the simulated run, restores, and asserts `oldname.txt` exists while `newname.txt` is gone.
- Rule candidate: When a checklist calls for coverage "across" a set of changed-file states, verify more than one representative state — include create, modify, delete, and rename.

### Finding 2
- Severity: low
- Category: test-gap
- Summary: There is no validation that `jjRestoreCheckpoint` surfaces a meaningful error when given an invalid or expired `opId`.
- Evidence: `jjRestoreCheckpoint` throws if `jj op restore <bad-id>` fails. The callers in `index.ts` catch the exception and show `e.message` to the user, but the validation script only exercises the success path with real, valid operation IDs.
- Recommendation: Add a lightweight negative test in `validate-vazir-jj-exact-restore.mts` that calls `jjRestoreCheckpoint(cwd, "00000000")` inside a real JJ repo and asserts the expected exception is thrown.
- Rule candidate: Every command that shells out to a backend operation needs at least one negative-path test verifying graceful failure when the backend rejects the input.
