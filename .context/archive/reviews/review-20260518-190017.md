## Findings

### Finding 1
- Severity: medium
- Category: bug
- Summary: `collectFossilAuditFiles` returns `null` immediately when `fossil diff --branch` throws, bypassing the `fossil changes` / `fossil extras` fallback.
- Evidence: In `.pi/extensions/vazir-context/index.ts`, the first `try/catch` block wraps the branch-wide diff query. If that command fails for any reason (old Fossil version, permissions, branch name issues), the catch returns `null` before the second `try` block that scans working-copy changes can run.
- Recommendation: Remove the early `return null` from the first catch so the function falls through to the working-copy scan on branch-diff failure.
- Rule candidate: —

### Finding 2
- Severity: low
- Category: workflow
- Summary: `registerVcsScaffold` is imported and invoked from both `vazir-context` and `vazir-tracker` entrypoints, creating a latent double-registration risk when the scaffold becomes non-empty.
- Evidence: `.pi/extensions/vazir-context/index.ts` calls `registerVcsScaffold(pi)` near its default export, and `.pi/extensions/vazir-tracker/index.ts` calls it in the same way. Today the function is a no-op, so there is no runtime impact.
- Recommendation: When VCS command behavior eventually migrates into `vazir-vcs`, remove the redundant scaffold call from one entrypoint to avoid duplicate command registration.
- Rule candidate: When no-op registration hooks are wired from multiple entrypoints, document which extension owns the eventual live registration so future migration stories cannot accidentally double-register commands.
