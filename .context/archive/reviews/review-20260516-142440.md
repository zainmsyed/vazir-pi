## Findings

### Finding 1
- Severity: high
- Category: bug
- Summary: `reviewFileTemplate` does not include a `## Fallow Findings` section, and `buildReviewInstruction` never tells the agent to create one, so `reviewFallowFindingsFromFile` always returns `[]` for real agent-produced reviews.
- Evidence:
  - `reviewFileTemplate` (helpers.ts:2397–2459) outputs `## Goal`, `## Checklist`, `## Findings`, `## Recommended Fixes`, `## Other Fixes`, and `## Completion Summary`. There is no `## Fallow Findings` placeholder.
  - `buildReviewInstruction` (helpers.ts:2354–2388) prepends the static-analysis prompt block with "Synthesise with your own inspection where relevant" but never instructs the agent to copy verbatim Fallow findings into a dedicated `## Fallow Findings` section.
  - `reviewFallowFindingsFromFile` (helpers.ts:1701–1730) only parses lines under `## Fallow Findings`. If the agent never creates that section, the parser returns `[]` and `appendFallowToComplaintsLog` never fires.
  - The validation scripts (`validate-vazir-fallow-recurrence.mts`, `validate-vazir-fallow-review-closeout.mts`) create mock review files with hand-written `## Fallow Findings` sections, so they pass even though real agent-produced reviews would lack the section entirely.
- Recommendation: Add a `## Fallow Findings` placeholder to `reviewFileTemplate` between `## Findings` and `## Recommended Fixes`. Add an explicit instruction in `buildReviewInstruction`: "If the Static Analysis Findings block above contains issues, copy them verbatim into a `## Fallow Findings` section. If none, write `No Fallow findings`."
- Rule candidate: When a backend produces structured findings that must be parsed later, the review template and instructions must explicitly direct the agent to preserve them in the expected section.

### Finding 2
- Severity: medium
- Category: bug
- Summary: Fossil bridge `runFallowAuditViaFossilBridge` copies `.context/` into the temp git repo, exposing Vazir brain files to Fallow analysis.
- Evidence:
  - `runFallowAuditViaFossilBridge` (index.ts:443–522) defines `excluded = new Set([".git", "node_modules", ".jj", ".fslckout", "_FOSSIL_", "dist", "build", "out"])`.
  - `.context` is not in the excluded set, so `.context/` files are copied via `copyContents(cwd, repoDir)` and committed into the temp repo.
  - Fallow running with `--base HEAD~1` will see `.context` files as new additions (since Fossil ignore-glob keeps them out of Fossil history) and may analyze them, producing noise or false positives in Vazir metadata.
- Recommendation: Add `.context` to the `excluded` set in `copyContents` so the temp repo mirrors only source and config files.
- Rule candidate: When creating a temp mirror of a repo for external tooling, exclude the project's own brain/metadata directories to prevent the tool from analyzing generated or internal files.

### Finding 3
- Severity: low
- Category: simplification
- Summary: `appendFallowToComplaintsLog` re-reads the complaints log from disk via `countFallowOccurrences` instead of counting from the already-parsed `existingEntries`.
- Evidence:
  - `appendFallowToComplaintsLog` (helpers.ts:1767–1819) parses `existingEntries` from the in-memory `lines` array for deduplication.
  - It then calls `countFallowOccurrences(cwd, finding.key)` (helpers.ts:1752–1765), which performs a fresh `readIfExists(complaintsLogPath(cwd))` and re-parses every line.
  - In a single-threaded runtime this is harmless but wasteful; the count could be derived from `existingEntries` directly.
- Recommendation: Compute the occurrence count from `existingEntries` instead of calling `countFallowOccurrences` inside the append loop, or inline the counting logic to avoid the extra disk read.
- Rule candidate: Avoid re-reading a file you already have parsed in memory; derive secondary computations from the in-memory representation.

### Finding 4
- Severity: low
- Category: workflow
- Summary: `parseComplaintsLogFallowEntry` regex anchors to end-of-line, making it brittle against future format extensions.
- Evidence:
  - The regex `/^([^|]+)\|\s*([^|]+)\|\s*\[fallow\]\s*(.+?)\s*\|\s*status:\s*([^|]+?)\s*$/i` anchors to `$`.
  - If the complaints-log format ever gains trailing fields (e.g., `| count: 3`), the regex will fail to match and the entry becomes invisible to recurrence counting.
- Recommendation: Relax the regex by removing the `$` anchor or making the status capture non-greedy and allowing trailing content: `/status:\s*([^|]+)/i`.
- Rule candidate: When parsing pipe-delimited log lines, do not anchor the regex to end-of-line unless the format is guaranteed frozen; allow benign trailing fields.

### Finding 5
- Severity: medium
- Category: test-gap
- Summary: No validation script asserts that `reviewFileTemplate` or `createReviewDraft` produces a review file containing a `## Fallow Findings` section.
- Evidence:
  - `validate-vazir-fallow-recurrence.mts` seeds its own `## Fallow Findings` section in mock review files.
  - `validate-vazir-fallow-review-closeout.mts` does the same.
  - Neither tests the actual template output or the instruction text for Fallow-preservation guidance.
  - `validate-vazir-review-design-compliance.mts` tests `reviewFileTemplate` for `## Design Compliance` but there is no equivalent test for `## Fallow Findings`.
- Recommendation: Add a validation script (or extend an existing one) that asserts: `reviewFileTemplate` includes a `## Fallow Findings` placeholder, and `buildReviewInstruction` includes text directing the agent to populate it.
- Rule candidate: When adding a new section to a structured output template, add a positive assertion that the template contains the section and a negative assertion that the instruction builder does not omit guidance for it.
