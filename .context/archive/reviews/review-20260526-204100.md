## Findings

### Finding 1
- Severity: medium
- Category: bug
- Summary: The JJ agent-run tracker in `tool_call` only reads `event.input.path`, ignoring the `filePath` fallback that `toolPathFromInput` already handles. If Pi ever issues a write/edit call with `filePath` instead of `path`, the run will be treated as a no-op and the checkpoint will be silently skipped.
- Evidence: `.pi/extensions/vazir-tracker/index.ts` line ~472 uses `const filePath = (event.input as any)?.path;`, while `toolPathFromInput(event.input)` three lines earlier already normalises `path || filePath || "(unknown file)"`. The existing Git snapshot branch right below the `useJJ` guard uses `const filePath = (event.input as any)?.path;` as well, so this is a copied pattern rather than a new bug, but it is still fragile.
- Recommendation: Reuse the already-resolved `file` variable from `toolPathFromInput(event.input)` for the JJ tracking block, or explicitly fall back to `filePath` so the behaviour matches the rest of the tracker.
- Rule candidate: When normalising tool input paths, always use the same helper at every consumption site; do not re-implement partial extracts that drift from the canonical fallback logic.

### Finding 2
- Severity: medium
- Category: test-gap
- Summary: The regression validation covers multi-turn runs, no-op skips, and restart-safe recovery, but misses several edge cases that could break the agent-run contract: `edit` tool calls (only `write` is tested), runs that touch multiple files in a single turn, store corruption recovery, and the 20-entry pruning boundary.
- Evidence: `scripts/validate-vazir-jj-agent-run-checkpoints.mts` exercises `toolName: "write"` in all three scenarios. There is no scenario for `toolName: "edit"`, no assertion that a run with two file writes records both files, no test for malformed JSON in the checkpoint store, and no test that appending the 21st checkpoint evicts the oldest entry.
- Recommendation: Add at least one `edit` scenario, a multi-file scenario, a corrupted-store scenario, and a prune-boundary scenario. Each can be a lightweight subprocess test following the existing pattern.
- Rule candidate: Every new persistence contract needs coverage for: (a) all mutating entry points, (b) bounded storage growth, and (c) graceful degradation on corrupt disk state.

### Finding 3
- Severity: low
- Category: simplification
- Summary: `AgentRunCheckpoint.postRunOpId` is captured and persisted but never read by production code or tests. It adds conceptual weight to the data model without current utility.
- Evidence: `getLatestUndoableAgentRun` only returns `preRunOpId` to the restore logic. The validation script asserts `preRunOpId`, `prompt`, and `files`, but never `postRunOpId`. No downstream consumer references the field.
- Recommendation: Either remove `postRunOpId` until a future story needs it, or add a comment explaining why it is being stored now (e.g. for later milestone-checkpoint UX). Keeping unused fields in a persisted schema creates migration risk if the design changes.
- Rule candidate: Do not persist fields in a schema until there is a committed consumer; if stored speculatively, document the planned consumer and target story.

### Finding 4
- Severity: low
- Category: workflow
- Summary: `saveAgentRunCheckpoint` failures in `agent_end` are silently swallowed. A full disk, permissions error, or malformed path would leave the user believing the run is undoable when the checkpoint was never written.
- Evidence: `.pi/extensions/vazir-tracker/index.ts` wraps the entire `saveAgentRunCheckpoint` call in `try { ... } catch { /* silent */ }`. The same silent pattern is used for `persistCurrentJjCheckpointLabel` and `autoDescribeCurrentJjChange`, but those are best-effort niceties; losing the undo record is a functional failure.
- Recommendation: At minimum, surface a `warning` notification when the checkpoint cannot be persisted, so the user knows "Undo last agent run" will not be available for this turn.
- Rule candidate: Silent catch blocks are acceptable for cosmetic or best-effort operations, but never for structural persistence that downstream user actions depend on.

## Completion Summary
All four recommended fixes are complete.

1. **`tool_call` JJ tracking** — Replaced the fragile `.path`-only read with the already-normalised `file` variable from `toolPathFromInput(event.input)`. This ensures `filePath` fallback keys are handled identically for both edit-stream tracking and agent-run checkpoint tracking.

2. **Validation expansion** — Added four new subprocess-isolated scenarios to `scripts/validate-vazir-jj-agent-run-checkpoints.mts`:
   - `editTool` — verifies that `toolName: "edit"` is tracked the same as `write`.
   - `multiFile` — verifies that a single run touching two files records both paths.
   - `corruptedStore` — verifies that malformed JSON in the checkpoint store is ignored and a fresh checkpoint can still be written.
   - `pruneBoundary` — verifies that the 20-entry cap is enforced by dropping the oldest checkpoints.

3. **`postRunOpId` removal** — Removed the speculative `postRunOpId` field from `AgentRunCheckpoint` in both `.pi/extensions/vazir-tracker/vcs.ts` and `.pi/lib/vazir-vcs-helpers.ts`, and from the save site in `index.ts`. The persisted schema now only contains fields with active consumers.

4. **Error surfacing** — Changed the silent `catch { /* silent */ }` around `saveAgentRunCheckpoint` in `agent_end` to a `catch (e: any)` that emits `ctx.ui?.notify?.(message, "warning")` when the checkpoint cannot be persisted.

The unchecked `Other Fixes` item (`validate-vazir-status-chrome.mts` failure) is a pre-existing issue unrelated to story-028; it stems from Fossil co-detection in the test environment and is out of scope for this story.

Verification: re-ran the new validation script standalone (all 7 scenarios pass) and the full aggregate suite (all story-028-related validators pass; the only failure is the pre-existing status-chrome test).
