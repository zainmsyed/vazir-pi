## Findings
### Finding 1
- Severity: medium
- Category: bug
- Summary: The `/test-help` handler calls `showMarkdownViewer` without verifying that `ctx.ui.custom` is available. `showSelectionList` gracefully falls back to `ctx.ui.select` when overlays are unavailable, but `showMarkdownViewer` does not, so non-UI environments crash after the user makes a selection.
- Evidence: `showSelectionList` checks `typeof ctx.ui?.custom !== "function"` and falls back to `ctx.ui.select`, returning a string value. The `/test-help` handler then unconditionally calls `showMarkdownViewer(ctx, doc.command, ...)` which immediately invokes `ctx.ui.custom<void>(...)`. If `custom` is missing, this throws. Other commands in the same file (e.g., `/design`) gate overlay usage behind `if (ctx.hasUI)`.
- Recommendation: Add an early guard in the `/test-help` handler — either check `ctx.hasUI` before starting the flow, or verify `typeof ctx.ui?.custom === "function"` and return a text-only fallback if overlays are unavailable.
- Rule candidate: When a handler chains multiple overlay helpers, verify that the required UI primitives are available before starting the flow, especially when one helper has a fallback path that the next helper lacks.

### Finding 2
- Severity: low
- Category: test-gap
- Summary: Story-039 introduces a new command path (`/test-help`) with selectable list → detail overlay → loop-back behavior, but there is no automated test or validation script exercising this path.
- Evidence: No new validation script was added to `scripts/`, and existing validation scripts do not cover the `/test-help` command or the loop-back overlay pattern.
- Recommendation: Add a lightweight validation script that exercises the command detail overlay rendering and the loop-back behavior, or extend `scripts/validate-vazir-ui-helpers.mts` with a mock command detail scenario.
- Rule candidate: Prototype commands that validate new UX patterns should include at least one automated smoke test so regressions in the pattern are caught before the production wiring story.

### Finding 3
- Severity: low
- Category: simplification
- Summary: The mock command schema and inline data in `/test-help` will need to be extracted and duplicated for the real registry in story-040. The current inline structure is not reusable.
- Evidence: `mockDocs` is defined entirely inside the `/test-help` handler with no exported type or helper. The rendering logic (building `mdLines`, calling `showMarkdownViewer`) is also inline.
- Recommendation: For story-040, extract a `CommandDoc` interface and a shared command registry into `.pi/lib/vazir-ui.ts` or `.pi/extensions/vazir-tracker/chrome.ts` so the schema and rendering logic can be reused by both `/test-help` and the eventual Ctrl+? wiring.
- Rule candidate: When a prototype validates a schema, extract the schema type and rendering helper into a shared module as part of the production follow-up story so the prototype knowledge is preserved.
