## Findings

### Finding 1
- Severity: medium
- Category: bug
- Summary: Repair inserts missing frontmatter keys at the first blank line, splitting the frontmatter block instead of keeping it contiguous.
- Evidence: In the live repair test, a corrupted review with only `**Status:**`, `**Scope:**`, and `**Story:**` was repaired to: `# Corrupted Review` then newly inserted `**Created:**`, `**Completed:**`, `**Focus:**`, `**Trigger:**`, a blank line, and only then the original `**Status:**` block. The frontmatter keys are no longer in the canonical order or contiguous block expected by `reviewFileTemplate`.
- Recommendation: Collect or rewrite the frontmatter as one contiguous block at the top of the file, preserving existing key order and inserting missing keys in canonical position.
- Rule candidate: When repairing structured frontmatter, keep the repaired block contiguous and in the canonical template order.

### Finding 2
- Severity: medium
- Category: bug
- Summary: `ensureReviewSection` appends missing sections at the end of the file, so repaired reviews do not match the canonical section order.
- Evidence: A review missing `## Goal`, `## Checklist`, etc. gets those sections appended after `## Findings` and `## Recommended Fixes`. The template defines `Goal` → `Checklist` → `Findings` → `Fallow Findings` → `Recommended Fixes` → `Other Fixes` → `Completion Summary`.
- Recommendation: Insert missing sections in canonical order relative to existing sections, or rebuild the section skeleton in order while preserving user content.
- Rule candidate: Structural repair should restore the canonical document order, not only satisfy the validator.

### Finding 3
- Severity: medium
- Category: bug
- Summary: File deletion while a review is suspended is treated as a meaningful delta, causing the flow to unsuspend, fail repair, and re-emit an exhaustion warning.
- Evidence: `hasReviewFileChanged` returns `previousHash !== undefined` when the file is missing. `prepareReviewForCloseout`/`prepareManualReviewForCloseout` then clear `suspended` and `repairAttempts`, run validation/repair against a missing file, and emit `could not be automatically repaired`.
- Recommendation: Treat a missing file while suspended as unchanged so the flow stays suspended; only resume when the file exists and its content hash differs.
- Rule candidate: Suspension resume should require an existing file with a verifiable content change, not mere absence.

### Finding 4
- Severity: low
- Category: simplification
- Summary: `prepareManualReviewForCloseout` and `prepareReviewForCloseout` duplicate the same validation, repair, attempt-counting, suspension, and persistence logic.
- Evidence: Both functions check suspension, hash delta, validate, repair up to `MAX_*_ATTEMPTS`, persist state, and emit an exhaustion warning. The only differences are the map type and the warning message.
- Recommendation: Extract a shared helper parameterized by the pending request type, map, max attempts, and warning copy.
- Rule candidate: When two lifecycle helpers differ only by target state container, extract a single parameterized implementation.

### Finding 5
- Severity: low
- Category: test-gap
- Summary: The regression suite does not exercise the repair path triggered from `/complete-story` `handleCommand` resumption.
- Evidence: `scripts/validate-vazir-review-loop.mts` tests `turn_end` repair and suspension, but the `handleCommand` branch that also calls `prepareReviewForCloseout` is only covered indirectly by `validate-vazir-complete-story.mts` with a valid review file.
- Recommendation: Add a scenario that seeds a persisted closeout state with a malformed review file and invokes `/complete-story`, asserting repair, preservation, and the closeout prompt.
- Rule candidate: Every entry point that can trigger recovery should have a representative regression test.

### Finding 6
- Severity: low
- Category: bug
- Summary: `repairReviewDocument` does not preserve the original `Trigger` value when it is missing; it defaults to `manual`.
- Evidence: In the live test, a review created by `/complete-story` had its `Trigger` lost during corruption; after repair it became `manual` instead of `complete-story`.
- Recommendation: When adding a missing `Trigger`, prefer a default that matches the known origin if available, or leave a placeholder that does not misclassify complete-story reviews as manual.
- Rule candidate: —

## Completion Summary
All six recommended fixes were implemented and verified:

1. **Frontmatter repair** — `rebuildReviewFrontmatter` now strips the old frontmatter block and emits a single contiguous block in canonical order (`Status`, `Created`, `Completed`, `Scope`, `Story`, `Static analysis`, `Focus`, `Trigger`).
2. **Section order** — `ensureReviewSectionsInOrder` rebuilds the section skeleton in canonical order while preserving existing section bodies and placeholders.
3. **Missing-file resume delta** — `hasReviewFileChangedForResume` now returns `false` when the review file is missing, so a suspended flow stays suspended instead of looping through repair exhaustion.
4. **Shared closeout helper** — New `prepareReviewFileForCloseout` in `helpers.ts` consolidates validation, bounded repair, suspension, and persistence logic; both `prepareReviewForCloseout` (complete-story) and `prepareManualReviewForCloseout` (manual review) delegate to it.
5. **handleCommand regression** — `scripts/validate-vazir-review-loop.mts` scenario 7 seeds a malformed persisted closeout state, invokes `/complete-story`, and asserts repair, preservation, and the closeout prompt.
6. **Trigger preservation** — `repairReviewDocument` now defaults a missing `Trigger` to `—` instead of `manual`, avoiding misclassification when the original value is unknown.
