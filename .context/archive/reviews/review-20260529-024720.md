## Findings

### Finding 1
- Severity: medium
- Category: bug
- Summary: `VazirPanel.render` can throw `RangeError` on extremely narrow terminals because `"─".repeat(width - 2)` is not clamped.
- Evidence: In `.pi/lib/vazir-ui.ts`, `VazirPanel.render` computes `const top = this.bg(this.borderFg(`┌${"─".repeat(width - 2)}┐`));` and similar lines for divider and bottom. If `width` is 0 or 1 (e.g., a very narrow terminal or unexpected overlay sizing), `repeat(-2)` or `repeat(-1)` throws. The `innerWidth` is defensively clamped with `Math.max(1, width - 4)`, but the border repeat expressions are not.
- Recommendation: Clamp every border repeat to at least 1: `const borderInner = Math.max(1, width - 2);` and use `"─".repeat(borderInner)` for top, divider, and bottom borders.
- Rule candidate: Any `String.repeat(n)` in TUI render paths must guard against `n < 0` because terminal width can be arbitrarily small.

### Finding 2
- Severity: medium
- Category: test-gap
- Summary: The validation stub for `truncateToWidth` does not implement the `pad` parameter, so the width-alignment regression test is a false positive.
- Evidence: `scripts/lib/validation-harness.mts` defines `exports.truncateToWidth = (str, width, ellipsis = '…') => str.length > width ? str.slice(0, width - ellipsis.length) + ellipsis : str;`. The real pi-tui `truncateToWidth` accepts a 4th `pad` parameter that ANSI-safely pads short lines to exact width. `scripts/validate-vazir-ui-helpers.mts` passes `true` for `pad`, but the stub ignores it. During implementation, this exact gap allowed a border-misalignment bug (title line unpadded) to slip through manual visual validation because the unit tests passed.
- Recommendation: Update the stub to accept and honor the `pad` parameter, or at minimum assert that `pad` calls receive correct behavior. Alternatively, stub `truncateToWidth` with a simple passthrough to a real implementation that counts ANSI escapes.
- Rule candidate: When a validation stub replaces a real function, the stub must support every parameter that production code calls; otherwise the test suite gives false confidence.

### Finding 3
- Severity: low
- Category: test-gap
- Summary: No validation exercises the default (non-destructive) selection-list path.
- Evidence: `scripts/validate-vazir-ui-helpers.mts` tests `showSelectionList` with `{ destructive: true }` in `scenarioSelectionListDefaultSafeFocus`, but there is no scenario that calls it without `destructive` or asserts that the first item (not the first safe item) receives initial focus.
- Recommendation: Add a scenario that calls `showSelectionList` without the `destructive` option and asserts `setSelectedIndex(0)` behavior.

### Finding 4
- Severity: low
- Category: simplification
- Summary: The overlay anchor union type is duplicated across both option interfaces.
- Evidence: `ShowSelectionListOptions` and `ShowMarkdownViewerOptions` each declare the identical 9-value anchor union: `"center" | "top-center" | ... | "bottom-right"`.
- Recommendation: Extract a shared `type OverlayAnchor = ...` alias in `vazir-ui.ts` and reference it from both interfaces.
- Rule candidate: When the same literal union appears more than once in a module, extract a named type alias to reduce drift during future changes.

### Finding 5
- Severity: low
- Category: dead-code
- Summary: Pre-truncating title and help text to 76 characters inside `showSelectionList` is redundant because `VazirPanel` already truncates to `innerWidth`.
- Evidence: In `.pi/lib/vazir-ui.ts`, `showSelectionList` passes `theme.fg("accent", theme.bold(truncateToWidth(title, 76, "…")))` to `VazirPanel`, which then calls `truncateToWidth(this.title, innerWidth, "", true)`. Since `innerWidth` is at most `width - 4` (default width 60% with minWidth 50), the 76-char pre-truncation is almost always a no-op and never prevents overflow. The same pattern appears for help text.
- Recommendation: Pass the raw title and help strings directly to `VazirPanel` / child `Text` components; remove the 76-char pre-truncation.
- Rule candidate: —
