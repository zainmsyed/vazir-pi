## Findings

### Finding 1
- Severity: low
- Category: workflow
- Summary: `scripts/debug-complete-story.mts` was an unused debug script left behind during development
- Evidence: Fallow static analysis flagged `[unused-files] scripts/debug-complete-story.mts`. The file was a manual reproduction script created while debugging `assessStoryCompletionReadiness` behaviour.
- Recommendation: Delete the file before closing the story.
- Rule candidate: When adding temporary debug or reproduction scripts during development, delete them before the story closeout or add the path to `.gitignore` exclusion patterns if they must persist.

### Finding 2
- Severity: medium
- Category: workflow
- Summary: Circular import between `vazir-story` and `vazir-tracker`
- Evidence: `vazir-story/index.ts` imports `refreshVcsState` from `../vazir-tracker/index.ts`, while `vazir-tracker/index.ts` imports `registerStoryScaffold`, `handleStoryCommand`, `handleImplementCommand`, and `handleFixCommand` from `../vazir-story/index.ts`.
- Recommendation: Break the cycle by having `vazir-story` call `refreshVcsState` through a callback or by moving the VCS refresh helper to `vazir-helpers.ts` (or a shared neutral module).
- Rule candidate: When extracting behaviour into a new extension, avoid importing from the extension that consumes your exports; move shared cross-cutting utilities into `.pi/lib` or a neutral helper module.

### Finding 3
- Severity: low
- Category: simplification
- Summary: Duplicate `lastUserPrompt` module-level state in `vazir-tracker` and `vazir-story`
- Evidence: Both `.pi/extensions/vazir-tracker/index.ts:66` and `.pi/extensions/vazir-story/index.ts:61` declare independent `let lastUserPrompt = ""` variables. Both `input` handlers write to their own copy. The values stay in sync because they read from the same event, but this is redundant state.
- Recommendation: Consolidate `lastUserPrompt` into a single location (e.g., a shared helper in `.pi/lib`) or have the tracker own it and expose a getter if the story layer needs access.
- Rule candidate: When extracting event handlers into a new extension, audit whether the old extension still maintains independent copies of state that the new extension now owns.

### Finding 4
- Severity: high
- Category: bug
- Summary: `assessStoryCompletionReadiness` initially used an incorrect issue-status filter after extraction, blocking valid closeouts
- Evidence: The first extracted version checked `status !== "resolved" && status !== "closed" && status !== "fixed"`, which incorrectly treated `confirmed` as a blocker. This caused `validate-vazir-complete-story.mts` to fail with the story marked as "not ready to complete yet" even when checklist items were checked and issues were resolved. The filter was restored to `status === "pending" || status === "unresolved" || status === "reopened"` to match the original helper in `vazir-context/helpers.ts`.
- Recommendation: Already fixed during extraction. No further action required.
- Rule candidate: When extracting state-machine logic, validate the golden path end-to-end after every integration, not just the extracted module in isolation.

### Finding 5
- Severity: high
- Category: bug
- Summary: `startLearnedRuleCloseout` had an argument-order bug that caused `TypeError: pi.sendMessage is not a function`
- Evidence: In the initial extracted code, `startLearnedRuleCloseout` was a synchronous helper that only had access to `ctx` (not `pi`). It passed `ctx` as the first argument to `sendInternalAgentMessage`, which expected `pi`. The validation harness surfaced this immediately: `TypeError: pi.sendMessage is not a function at sendInternalAgentMessage`. The signature was changed to accept `pi` explicitly.
- Recommendation: Already fixed during extraction. No further action required.
- Rule candidate: When a helper is extracted from a closure that captured a runtime object (like `pi`), update the helper signature to accept that object explicitly and verify every call site passes it correctly.
