## Findings

### Finding 1
- Severity: critical
- Category: bug
- Summary: After `/complete-story` triggers a readiness review and the agent finishes its turn, `agent_end` silently returns when blockers still exist — the user never sees `promptReadyCloseout` and receives no explanation why.
- Evidence: `.pi/extensions/vazir-story/index.ts` lines 213–215: inside `onStoryAgentEnd`, after calling `assessStoryCompletionReadiness` and `listCompletionBlockers`, the code has a bare `if (blockers.length > 0) { return; }` with no notification or fallback. If the agent failed to check off every checklist item, resolve every open issue, or write a non-empty completion summary, the closeout prompt (`promptReadyCloseout`) is skipped entirely and the session ends silently.
- Recommendation: Replace the silent return with a `ctx.ui.notify(...)` that tells the user which blockers remain and instructs them to re-run `/complete-story` after fixing them. Alternatively, re-send the readiness instruction so the agent can continue on the next turn.
- Rule candidate: Every state-machine branch that aborts a user-facing workflow must emit a diagnostic so the user knows why the expected prompt did not appear.

### Finding 2
- Severity: high
- Category: workflow
- Summary: Circular dependency between `vazir-vcs` and `vazir-tracker` — the extracted extension imports UI helpers and VCS primitives from the extension it is supposed to replace.
- Evidence: `vazir-vcs/index.ts` imports 15 functions from `../vazir-tracker/chrome.ts` (`applyWorkingMessage`, `beginToolActivity`, `changedFiles`, `ensureSessionChromeMounted`, `refreshWidgets`, `setVcsFlags`, `startFooterRefreshTicker`, `tearDownChromeSession`, etc.) and 20+ functions from `../vazir-tracker/vcs.ts` (`detectGitRepo`, `jjCheckpointChoices`, `syncChanges`, `inspectVcsToolGuard`, `gitRestoreCheckpoint`, etc.). At the same time, `vazir-tracker/index.ts` imports `attachVcsWorkflow` from `../vazir-vcs/index.ts`.
- Recommendation: Move shared VCS primitives (checkpoint helpers, diff/sync functions, tool guards) into a neutral module under `.pi/lib` or directly into `vazir-vcs` so that `vazir-vcs` does not depend on `vazir-tracker`. UI-specific helpers should remain in `vazir-tracker/chrome.ts` and be consumed by `vazir-vcs` only through a narrow, explicitly-versioned interface.
- Rule candidate: When extracting behaviour into a new extension, avoid importing from the extension that consumes your exports; move shared cross-cutting utilities into `.pi/lib` or a neutral helper module.

### Finding 3
- Severity: medium
- Category: scope-drift
- Summary: The actual VCS business logic never left `vazir-tracker/vcs.ts` — `vazir-vcs` is only an orchestration shim.
- Evidence: `vazir-vcs/index.ts` delegates all concrete work to imports from `vazir-tracker/vcs.ts`: `syncChanges` for repo-state syncing, `inspectVcsToolGuard` for safety checks, `jjCheckpointChoices` / `listGitCheckpoints` for checkpoint listings, `gitSnapshotFile` / `gitRestoreCheckpoint` for snapshot management, and `jjRestoreCheckpoint` / `jjDiffFile` for JJ operations. The only new code in `vazir-vcs` is mode-resolution settings logic and command wrappers.
- Recommendation: Migrate the implementations from `vazir-tracker/vcs.ts` into `vazir-vcs` (or a new `.pi/lib/vazir-vcs-helpers.ts`) so the owning extension truly owns the VCS workflow end-to-end, leaving `vazir-tracker/vcs.ts` as a thin re-export compatibility layer during transition.
- Rule candidate: After extracting helpers to a new module, delete the original copies from the source module to prevent drift and confusion.

### Finding 4
- Severity: medium
- Category: bug
- Summary: Both `vazir-vcs` and `vazir-tracker` try to start the footer refresh ticker during `session_start`, creating a fragile singleton race.
- Evidence: `vazir-vcs/index.ts` `session_start` handler calls `startFooterRefreshTicker(...)` around line 667. `vazir-tracker/index.ts` `session_start` handler also calls `startFooterRefreshTicker(...)` around line 58. `chrome.ts` guards against double-start with `if (footerRefreshTicker || !currentFooterSnapshot) return;`, so the second call is silently dropped. If extension load order changes, the surviving ticker may be attached to the wrong callback chain.
- Recommendation: Remove `startFooterRefreshTicker` from `vazir-tracker/index.ts` and let `vazir-vcs` own it exclusively, since VCS state refresh is the semantic trigger for footer updates. Document the ownership in a comment.
- Rule candidate: When extracting lifecycle handlers into a new extension, remove the original registration to avoid duplicate event processing.

### Finding 5
- Severity: low
- Category: simplification
- Summary: `vazir-vcs` default export is still a no-op even though all real VCS behaviour now lives in the extension.
- Evidence: `export default function (_pi: ExtensionAPI) { // Intentional no-op. vazir-context calls registerVcsScaffold() explicitly ... }`. This means if Pi ever loads `vazir-vcs` standalone (without `vazir-context` calling `registerVcsScaffold`), the extension does nothing.
- Recommendation: Change the default export to call `registerVcsScaffold(pi)` so the extension is self-registering, and remove the no-op fallback. The `WeakSet` guard in `registerVcsScaffold` already prevents double-registration if context also calls it.
- Rule candidate: Remove no-op registration hooks once the real behavior has migrated to the owning extension.

### Finding 6
- Severity: low
- Category: test-gap
- Summary: Validation scripts leave `.context/settings/jj-checkpoint-labels.json` dirty with test artifacts, causing spurious workspace edits after the suite runs.
- Evidence: After running `npm test`, `fossil status` reports `.context/settings/jj-checkpoint-labels.json` as locally edited even though `fossil diff` shows no textual difference. The file contains synthetic labels injected by `validate-vazir-checkpoint-labels.mts`.
- Recommendation: Update the checkpoint-labels validation to use a temporary settings directory (e.g. `.context/settings/.test-${nonce}`) or explicitly restore the original file content in a `finally` block. Add a post-suite assertion that the workspace is clean.
- Rule candidate: When creating a temp mirror of a repo for external tooling, exclude the project's own brain/metadata directories to prevent the tool from analyzing generated or internal files.

### Finding 7
- Severity: low
- Category: simplification
- Summary: `vazir-vcs` input handler duplicates the `/impliment` → `/implement` normalization already owned by `vazir-story`.
- Evidence: `vazir-vcs/index.ts` line 633: `if (event.text?.trim() === "/impliment") { event.text = "/implement"; }`. `vazir-story/index.ts` lines 92 and 98 contain the same normalization in `normalizeTrackerInputText` and `onStoryInput`.
- Recommendation: Remove the normalization from `vazir-vcs` and let `vazir-story` own it exclusively, since story lifecycle is the correct semantic owner for command-name typos.
- Rule candidate: When the same string-replacement sequence appears in two or more distinct code paths, extract it into a named helper so future changes to the output format happen in one place.
