## Findings
### Finding 1
- Severity: medium
- Category: test-gap
- Summary: Two updated validation scripts still load `vazir-story` as a second module instance, which no longer matches production wiring and can hide shared-state regressions.
- Evidence: `scripts/validate-vazir-fix-routing.mts` and `scripts/validate-vazir-story-status-guard.mts` now call `loadExtensionModule("vazir-story", `${Date.now()}-story`)` while also loading `vazir-tracker` or `vazir-context`, both of which import `../vazir-story/index.ts` without a cache key. `scripts/lib/validation-harness.mts` appends the cache key as `?t=...`, so these tests instantiate a second copy of `vazir-story`. Story-021 already hit this exact class of failure in `validate-vazir-complete-story.mts`, where duplicate `pendingCompleteStoryRequests` state broke the closeout flow until the cache-busted load was removed.
- Recommendation: Remove the cache-busting key from the direct `vazir-story` loads in the affected validation scripts, or avoid separately loading `vazir-story` when another loaded extension already imports it. Keep validation harness module identity aligned with production wiring whenever shared in-memory state is involved.
- Rule candidate: When a validation script loads an extracted extension alongside another extension that already imports it, use the same module instance as production instead of cache-busting one side into a second copy.
