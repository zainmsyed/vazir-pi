## Findings
### Finding 1
- Severity: medium
- Category: test-gap
- Summary: The new `/vazir-init` Fossil-theme validation does not verify that the actual generated CSS/header/footer payloads survive the Fossil SQL write path, so escaping or multiline-write regressions could still ship undetected.
- Evidence: `scripts/validate-vazir-init.mts` stubs `fossil sql` by writing the entire SQL statement into `.fake-fossil-{css,header,footer}.txt` for `REPLACE INTO config(...)` calls, then only asserts that those files contain `managed-by: vazir`. Because the fake backend does not reconstruct the stored value, the test never proves that `applyManagedFossilTheme()` writes valid asset contents after SQL escaping, quote doubling, and multiline transport through `fossil sql`.
- Recommendation: Strengthen the Fossil init validation stub to persist the decoded `value` payload (not the whole SQL statement) and add assertions that the stored CSS/header/footer exactly contain representative generated theme content, not just the managed marker.
- Rule candidate: When a validation stub stands in for a persistence layer, make it store and verify the same payload shape that production reads back so escaping bugs cannot hide behind marker-only assertions.
