## Findings
### Finding 1
- Severity: high
- Category: regression
- Summary: Moving final `/complete-story` completion into `turn_end` can trigger the story-status guard on the same turn, causing real interactive closeouts to prompt for reversal or revert unexpectedly.
- Evidence: `createCompleteStoryController.handleTurnEnd()` now calls `finishLearnedRuleCloseout(...)` directly when the phase is `learned-rule-closeout` (`.pi/extensions/vazir-context/complete-story.ts:921-923`), and that path finalizes with `completeStoryNow(...)` / `completeStoryAndCommitNow(...)` inside `turn_end` (`.pi/extensions/vazir-context/complete-story.ts:656-660`, `475-493`). The shared status guard still snapshots story frontmatter in `before_agent_start` (`.pi/extensions/vazir-context/index.ts:1010-1014`) and, in `agent_end`, queues any unapproved `complete` transition for confirmation or reversion based only on `lastUserPrompt` text (`.pi/extensions/vazir-context/index.ts:1179-1190`). Menu choices from `/complete-story` do not update `lastUserPrompt`, so a successful closeout can be treated like an unsolicited agent status change in a real session. The updated validation harnesses do not catch this because they emit `turn_end`/`agent_end` directly without a preceding `before_agent_start` snapshot in the complete-story scenarios.
- Recommendation: Keep final story completion for this flow in a non-guarded path after the status-check phase, or explicitly mark `/complete-story`-owned closeouts as user-approved for the subsequent `agent_end` pass. Add a regression that emits `before_agent_start` → `turn_end` → `agent_end` for a successful closeout so the guard cannot silently regress again.
- Rule candidate: When an extracted workflow changes when story frontmatter is written, re-run the full lifecycle including any status-guard snapshots so user-approved transitions are not mistaken for unsolicited agent changes.
