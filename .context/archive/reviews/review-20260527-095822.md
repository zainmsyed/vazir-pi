## Findings

### Finding 1
- Severity: medium
- Category: bug
- Summary: The fallback undo label promises "undo last agent turn" but may restore to an arbitrary milestone (e.g., an explicit save from hours ago) when no agent-run checkpoint exists.
- Evidence: In `.pi/extensions/vazir-tracker/index.ts`, `runCheckpointRestore` builds `undoLabel` as either `Undo last agent run — …` or `Previous checkpoint — undo last agent turn`. When `latestRun` is null but `milestones.length > 0`, the handler restores to `milestones[0]` (the most recent milestone), which could be an `explicit-save` or `workflow-boundary` from any earlier time — not the "last agent turn."
- Recommendation: Change the fallback label to something honest like `Restore latest milestone — …` when `latestRun` is null, or disable the option and only show the milestone browser. Do not promise "undo last agent turn" unless the restore target is guaranteed to be the pre-run state of the most recent agent turn.
- Rule candidate: UI labels that describe a restore action must accurately describe what will be restored; fallbacks to broader categories need relabeling.

### Finding 2
- Severity: low
- Category: simplification
- Summary: The entire milestone helper layer (~50 lines) is duplicated byte-for-byte between `.pi/extensions/vazir-tracker/vcs.ts` and `.pi/lib/vazir-vcs-helpers.ts`.
- Evidence: `Milestone`, `MilestoneStore`, `MILESTONE_MAX`, `milestonesPath`, `loadMilestones`, `pruneMilestones`, `saveMilestone`, `milestoneLabel`, and `getMilestoneChoices` are identical in both files. The two files already diverge in other helpers, but the milestone code is a pure copy.
- Recommendation: If one file is meant to be the source of truth, export the helpers from there and re-export from the other. If both must remain standalone, add a cross-reference comment in each file so future edits don't drift.
- Rule candidate: When the same logic block is pasted into two files, add a cross-reference comment linking both copies so the next editor knows to keep them in sync.

### Finding 3
- Severity: low
- Category: bug
- Summary: `saveMilestone` failures in the `agent_end` handler are silently swallowed, hiding disk/permission issues from the user.
- Evidence: In `.pi/extensions/vazir-tracker/index.ts` `agent_end`, the `saveAgentRunCheckpoint` call reports failures via `ctx.ui?.notify?.(…, "warning")`, but the `saveMilestone` call immediately below it has an empty `catch { }` with a comment saying "silent — milestone is best-effort enhancement."
- Recommendation: Report milestone save failures at the same level as checkpoint save failures (e.g., `ctx.ui?.notify?.("Failed to save milestone: …", "warning")`). "Best-effort" does not mean "invisible when it breaks."
- Rule candidate: Best-effort features should still surface failures via non-blocking notifications so users can distinguish "nothing happened" from "something broke."

### Finding 4
- Severity: low
- Category: dead-code
- Summary: `loadMilestones` is imported in `.pi/extensions/vazir-tracker/index.ts` but never used there.
- Evidence: Line 74 imports `loadMilestones` from `./vcs.ts`. The only milestone consumers in `index.ts` are `getMilestoneChoices` (line 908), `milestoneLabel` (lines 944, 966), and `saveMilestone` (lines 631, 974). `getMilestoneChoices` internally calls `loadMilestones`, so `index.ts` has no direct need for it.
- Recommendation: Remove the unused `loadMilestones` import from `index.ts`.
- Rule candidate: —

### Finding 5
- Severity: low
- Category: bug
- Summary: `milestoneLabel` can produce duplicate labels for distinct milestones, causing `labels.indexOf(pick)` in `runCheckpointRestore` to return the wrong milestone index.
- Evidence: `milestoneLabel` formats a label as `` `${t} · ${kindPrefix} · ${ms.label.slice(0, 50)}` `` where `t` comes from `toLocaleTimeString()` (locale-dependent, second-level precision). If two milestones of the same kind are created in the same second and share the same 50-character label prefix, their picker labels collide. In `runCheckpointRestore`, the restore logic uses `milestones[labels.indexOf(pick)]`, which returns the first match.
- Recommendation: Include a disambiguating token in `milestoneLabel` — either milliseconds, an ordinal index, or a short hash of the unique `id` — so that no two distinct milestones can share the same picker label.
- Rule candidate: Picker labels used as lookup keys must be guaranteed unique; never rely solely on user-provided text and time-of-day for uniqueness.

## Completion Summary
All five recommended fixes have been completed and verified.

1. **Misleading fallback undo label** — Changed `undoLabel` in `index.ts` to show `Restore latest milestone — …` when `latestRun` is null and milestones exist, and `No undo target available` when neither exists. The label now accurately describes what will be restored.

2. **Duplicated milestone helpers** — Added cross-reference comments at the top of the milestone helpers block in both `vcs.ts` and `vazir-vcs-helpers.ts` warning that the code is mirrored and must be kept in sync.

3. **Silent milestone save failures** — Replaced the empty `catch { }` in `agent_end` with `catch (e: any) { ctx.ui?.notify?.(…, "warning") }`, matching the error-reporting pattern used by `saveAgentRunCheckpoint`.

4. **Unused import** — Removed `loadMilestones` from the import list in `index.ts`.

5. **Milestone label collision** — Appended `· ${ms.id.slice(-4)}` to `milestoneLabel` in both `vcs.ts` and `vazir-vcs-helpers.ts`. Since `id` includes a millisecond timestamp, the suffix guarantees unique picker labels and eliminates the `labels.indexOf(pick)` collision risk.

Verification: `node --experimental-strip-types ./scripts/run-validations.mts` passes all story-030 related tests (`validate-vazir-jj-milestones.mts`, `validate-vazir-checkpoint-labels.mts`, `validate-vazir-jj-agent-run-checkpoints.mts`, `validate-vazir-jj-exact-restore.mts`).
