## Findings
### Finding 1
- Severity: medium
- Category: regression
- Summary: The managed Fossil theme claims to use `.context/design/` as its source of truth, but the generated CSS ignores the parsed design tokens and ships hard-coded colours, typography, spacing, and shape values instead.
- Evidence: In `.pi/lib/vazir-fossil-theme.ts`, `readFossilThemeDesignSpec()` parses `colours`, `typography`, `spacingAndShape`, and `componentConventions`, but `buildCss(spec)` does not consume those arrays when generating `:root` variables or layout values. The CSS always emits fixed constants like `--vz-bg: #1f201d;`, `--vz-radius-md: 14px;`, and the fixed font stacks regardless of the design files. The validation in `scripts/validate-vazir-fossil-theme.mts` only proves that `brandDirection` and `pageBoundaries` are read, not that the generated theme responds to token changes.
- Recommendation: Thread the parsed design tokens into the generated CSS/header/footer (or clearly narrow the helper's contract), and add regression assertions that changing representative design values in `.context/design/` changes the emitted managed theme assets.
- Rule candidate: When generated assets are described as design-spec-driven, make validation prove that representative spec changes affect the emitted output rather than only being read into metadata comments.
