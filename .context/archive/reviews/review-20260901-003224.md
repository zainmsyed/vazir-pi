## Findings
### Finding 1
- Severity: high
- Category: bug
- Summary: PATH is added to only one startup file, so the launcher may remain undiscoverable in the other normal Bash/Zsh shell mode.
- Evidence: `install.sh:132-155` selects exactly one Bash file (`.bash_profile`, `.bash_login`, `.profile`, or `.bashrc`) and exactly one Zsh file (`.zshrc`, `.zprofile`, `.zlogin`, or `.profile`). Bash login and interactive shells commonly read different files, as do Zsh login and interactive shells. The fresh-shell check at `install.sh:384-389` sources the selected file directly, so it does not prove the actual login/interactive startup chain will load the PATH entry.
- Recommendation: Model the login and interactive startup chains explicitly. Add the PATH block to the correct existing entry point(s), or add a guarded source handoff between the selected files, then test both `bash -lic`/`bash -ic` and `zsh -lic`/`zsh -ic` behavior where available.
- Rule candidate: —

### Finding 2
- Severity: medium
- Category: bug
- Summary: Launcher and profile setup can fail after the release has been moved, leaving a partial installation or a misleading nonzero result.
- Evidence: `install.sh:329-343` moves the verified extraction into `releases/<version>` before `write_launcher` and the compatibility-link operations. A failure writing `~/.local/bin/vazir`, creating the internal link, or later editing a shell profile in `install.sh:362-375` exits under `set -e`; the new release may remain orphaned, and profile-edit failure occurs after activation has already succeeded.
- Recommendation: Preflight the launcher/profile destinations before moving the release, make launcher preparation and profile edits nonfatal only after reporting an explicit warning, and remove any newly moved release on pre-activation failure. Keep the active switch as the final operation.
- Rule candidate: —

### Finding 3
- Severity: medium
- Category: simplification
- Summary: The production installer duplicates the path-policy implementation instead of using `src/install/path.ts`.
- Evidence: `src/install/path.ts` defines shell detection, profile selection, PATH idempotence, and managed-launcher detection, but `install.sh:132-155` and `install.sh:362-389` implement separate Bash versions. `scripts/validate-install-paths.mts` tests both the TypeScript helpers and the shell installer independently, so changes to the helper do not affect production behavior and the two implementations can drift.
- Recommendation: Establish one canonical implementation boundary: either generate/consume the same shell policy from the helper, or reduce `src/install/path.ts` to a testable specification used by the shell implementation. Add parity assertions for profile selection and PATH insertion.
- Rule candidate: When a validation or helper duplicates production policy, make the production path delegate to the canonical implementation or explicitly test parity between both implementations.

### Finding 4
- Severity: medium
- Category: test-gap
- Summary: WSL2 coverage validates the pure policy helper but not the installer’s actual WSL2 branch or Linux-home placement.
- Evidence: `scripts/validate-install-paths.mts:35-52` tests `evaluateHomePolicy` with injected WSL2 metadata, while the installer branch at `install.sh:105-114` reads the host `/proc` files directly and is never executed in a WSL2-like isolated environment. The integration tests therefore do not verify that the real installer rejects `/mnt` HOME values, emits the expected warning, or selects Linux placement under WSL2.
- Recommendation: Add an installer-level test seam for platform/home probing, or run the script in a controlled WSL2-like fixture, and assert the actual artifact target, install root, warning text, and PATH outcome.
- Rule candidate: —
